# Дизайн: резервные копии и история версий глав

_Дата: 2026-05-23_

---

## Контекст

Текст для писателя — сакральная вещь. Сейчас автосохранение перезаписывает контент каждые 700 мс без каких-либо версий. Случайное удаление абзаца, неудачная правка или закрытая вкладка — всё это необратимо. Задача: добавить страховку от потерь для всех пользователей и полноценную историю версий для Pro.

---

## Выбранный подход: «Страховка + Вехи»

Разделяет две потребности:

- **Free (страховка):** автоматические снимки по триггерам, хранить последние 10 на главу. Простой UI «Резервные копии» с кнопкой «Просмотр» и «Восстановить».
- **Pro (вехи):** те же авто-снимки (30 дней) + именованные снимки по кнопке, хранятся бессрочно. UI «История версий» с отдельной секцией именованных вех.

---

## Модель данных

```sql
create table chapter_versions (
  id          uuid primary key default gen_random_uuid(),
  chapter_id  uuid not null references chapters(id) on delete cascade,
  user_id     uuid not null references auth.users(id) on delete cascade,
  content     text not null,
  word_count  integer,
  label       text,       -- NULL = авто-снимок; строка = именованная веха (Pro)
  trigger     text not null
    check (trigger in ('beforeunload', 'chapter_switch', 'timer', 'manual')),
  created_at  timestamptz default now()
);

create index on chapter_versions (chapter_id, created_at desc);
create index on chapter_versions (chapter_id, label) where label is not null;
```

**RLS:** `auth.uid() = user_id` — единый паттерн проекта.

Разграничение Free/Pro — на уровне приложения, не в схеме:
- `label IS NOT NULL` — именованная веха, доступна только Pro.
- Лимит и TTL авто-снимков проверяются перед INSERT.

## Триггеры создания снимков

| Триггер | Событие | Free | Pro |
|---|---|---|---|
| `beforeunload` | закрытие вкладки/браузера | ✓ | ✓ |
| `chapter_switch` | переход на другую главу | ✓ | ✓ |
| `timer` | таймер активного редактирования | раз в 2 ч | раз в 30 мин |
| `manual` | кнопка «Сохранить текущую версию» | — | ✓ |

**Защита от дублей:** снимок не создаётся, если `content` идентичен последнему снимку этой главы. Сравнение по длине строки — достаточно для большинства случаев; если длина одинакова, проверяем полное совпадение.

**`beforeunload`:** отправляется через `fetch` с `keepalive: true` на Supabase REST (`/rest/v1/chapter_versions`), чтобы запрос не обрывался при закрытии вкладки. Обычный `supabase.from(...).insert(...)` не подходит — его промис не успевает выполниться.

## Стратегия хранения (pruning)

Pruning выполняется в той же транзакции что и INSERT — никаких cron-задач.

### Free

- Лимит: **10 авто-снимков** на главу.
- При превышении: удалить самый старый авто-снимок (`label IS NULL ORDER BY created_at ASC LIMIT 1`).
- Именованные вехи: недоступны.

### Pro

- Авто-снимки: хранить **30 дней**, удалять снимки старше `now() - interval '30 days'` при каждой записи.
- Именованные вехи: хранятся **бессрочно**, пока пользователь не удалит вручную.
- Жёсткого числового лимита нет, но 30-дневное окно при частоте 30 мин даёт ~1 440 авто-снимков на главу в худшем случае. При среднем TipTap JSON ~30 KB и Postgres PGLZ-сжатии (~60%) — ~18 KB на снимок, ~26 MB на активную главу за 30 дней. Приемлемо.

---

## Оценка роста БД

| Сценарий | Размер |
|---|---|
| Free-пользователь, 20 глав, 10 версий | ~2 MB (сжато) |
| Pro-пользователь, 20 глав, 30 дней × 30 мин | ~26 MB на главу, ~500 MB всего |
| 1 000 пользователей (200 Pro) | ~5–10 GB |

При 10 000 пользователей стоит рассмотреть вынос `content` в Supabase Storage, но это следующий этап.

### Модальное окно просмотра версии

Открывается по клику на любую карточку. Содержит:
- Заголовок: название вехи или дата/время снимка.
- Мета: дата, триггер, количество слов.
- Тело: readonly-текст главы в `.paper`-стиле (Source Serif 4, как в редакторе).
- Футер: кнопки «Отмена» и «Восстановить эту версию» (`.btn--primary`).

«Восстановить» открывает `ConfirmDialog` (уже есть в проекте): «Текущий текст главы будет заменён версией от [дата]. Это действие нельзя отменить.» При подтверждении — `updateChapterContent(chapterId, version.content)` + инвалидация кэша React Query.

## Ограничения и граничные случаи

- **Восстановление создаёт снимок:** перед заменой контента автоматически сохраняется снимок текущей версии с триггером `'beforeunload'` — чтобы можно было «отменить восстановление».
- **Смена плана Free → Pro:** авто-снимки сделанные на Free остаются, лимит не меняется ретроспективно. Новые снимки начинают жить по Pro-правилам.
- **Смена плана Pro → Free:** именованные вехи остаются (не удалять — это данные пользователя). Новые авто-снимки снова ограничены 10.
- **Глава удалена:** `ON DELETE CASCADE` на `chapter_id` — все версии удаляются автоматически.
- **Офлайн / ошибка сети:** при сбое `beforeunload`-запроса снимок теряется тихо (не показываем ошибку — вкладка уже закрывается). Остальные триггеры имеют стандартную обработку ошибок.

## Что не входит в первую итерацию

- Diff-просмотр (сравнение версий side-by-side) — сложно с TipTap HTML.
- Экспорт отдельной версии — по запросу пользователей.
- Версионирование на уровне книги (все главы разом) — отдельная фича.
- Автоматическое определение «важных» снимков (например, после большого объёма правок) — YAGNI.
