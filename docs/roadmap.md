### 🔴 Экспорт: переключатель «Заметки на полях как сноски» не работает

**Файл:** `src/pages/Export.tsx` (компонент опций экспорта).

**Что происходит:** переключатель отображается, но при экспорте заметки не появляются в документе как сноски — ни в DOCX, ни в EPUB, ни в FB2. Функционал заявлен в UI, но не реализован.

**Что сделать:**
- DOCX: вставлять заметки как `w:footnote` через docx.js (`FootnoteReferenceRun` + `FootnoteElement`).
- EPUB: добавлять `<aside epub:type="footnote">` с обратной ссылкой.
- FB2: использовать тег `<body name="notes">` + `<note>` с `id`.
- Привязка: у заметки должна быть позиция в тексте или номер абзаца — иначе непонятно, где ставить сноску. Временное решение: добавлять все заметки в конец главы как «Примечания автора».

### 🟡 Соседние заметки растут при длинном тексте

**Файл:** `src/pages/Notes.tsx` (или компонент карточки заметки).

**Что происходит:** грид/flex-контейнер карточек заметок выравнивает высоту по самой высокой карточке в строке — короткие заметки растягиваются до высоты длинных. Выглядит как пустые блоки.

**Что сделать:** `align-items: flex-start` (или `align-self: flex-start` на карточке) на контейнере. Если используется CSS Grid — убрать `align-items: stretch` (дефолт). Карточки должны иметь высоту по контенту.

### 🟡 Мерцание подчёркиваний спеллчека при исправлении слова

**Файл:** `src/components/RichEditor.tsx` (или TipTap `spellcheck`-логика).

**Что происходит:** при исправлении одного слова все остальные подчёркивания на мгновение исчезают, затем появляются снова. Причина — TipTap пересчитывает декорации всего документа при каждом изменении.

**Что сделать:** оптимизировать область пересчёта: декорировать только изменённый диапазон, а не весь документ. Альтернатива — дебаунс на пересчёт декораций (300–500 мс), чтобы мерцание не было заметно визуально.

### 🔴 Потеря текста при ошибке сети во время автосохранения

**Файл:** `src/pages/Editor.tsx`, функция `flush` (строки 78–93).

**Что происходит:** `pendingPatch.current = null` выставляется **до** `await updateChapter(...)`. Если запрос падает (офлайн, таймаут, 500 от Supabase), патч уже уничтожен — восстановить невозможно. Пользователь видит «Ошибка сохранения», но потерянный текст не вернуть.

```ts
// сейчас — НЕПРАВИЛЬНО:
pendingPatch.current = null;   // ← очищается до запроса
await updateChapter(id, patch) // ← если упало, patch потерян
```

**Фикс:**
```ts
// правильно — очищать только после успеха:
const patch = pendingPatch.current;
pendingPatch.current = null;
try {
  await updateChapter(id, patch);
} catch {
  pendingPatch.current = patch; // ← вернуть патч обратно
  setSaveState('error');
  // + запланировать retry через 3–5 сек
}
```

Дополнительно: показывать постоянный баннер при `saveState === 'error'` (не просто текст в статусбаре) — чтобы пользователь знал, что последнее изменение не сохранено.

### 🔴 Потеря последних изменений при закрытии вкладки

**Файл:** `src/pages/Editor.tsx`.

**Что происходит:** автосохранение работает с debounce 700 мс. Если пользователь закрыл вкладку в течение этих 700 мс после последнего нажатия клавиши — изменения потеряны. `flush` при unmount (`useEffect` cleanup) не успевает выполниться асинхронно при закрытии браузера.

**Фикс:** добавить `beforeunload`-обработчик, который синхронно вызывает `navigator.sendBeacon` с патчем (единственный способ гарантированно отправить запрос при закрытии вкладки):

```ts
useEffect(() => {
  const handler = () => {
    const patch = pendingPatch.current;
    const id = targetIdRef.current;
    if (!patch || !id) return;
    // sendBeacon — fire-and-forget, браузер не блокирует закрытие
    navigator.sendBeacon(
      `/api/chapters/${id}`,
      JSON.stringify(patch)
    );
  };
  window.addEventListener('beforeunload', handler);
  return () => window.removeEventListener('beforeunload', handler);
}, []);
```

Для этого нужен простой API-эндпоинт (Supabase Edge Function `PATCH /chapters/:id`) — прямой вызов Supabase JS SDK из `sendBeacon` не работает.

Альтернатива проще: перед закрытием делать `flush()` синхронно с `keepalive: true` через `fetch`. Но это работает только если запрос < 64 КБ (для главы — обычно ок).

### 🔴 Загрузка полного контента всех глав при открытии книги

**Файл:** `src/lib/chapters.ts`, функция `listChapters` (строка 43).

**Что происходит:** `select('*')` грузит поле `content` (весь HTML текст) для **каждой** главы при каждом открытии редактора. Сайдбар показывает только `title` и `status` — контент не нужен до тех пор, пока пользователь не кликнул на главу. Для книги 100 глав × 3 000 слов ≈ 600–800 КБ лишнего трафика при каждом открытии.

**Фикс:** разделить на два запроса.

```ts
// 1. Список глав — только метаданные (для сайдбара):
export async function listChapters(bookId: string) {
  return supabase
    .from('chapters')
    .select('id, title, position, status, words, created_at, updated_at')
    .eq('book_id', bookId)
    .order('position', { ascending: true });
}

// 2. Контент — только при выборе главы:
export async function getChapterContent(id: string) {
  return supabase
    .from('chapters')
    .select('id, content')
    .eq('id', id)
    .single();
}
```

В `Editor.tsx`: хранить `content` отдельно от списка глав. При `selectChapter(id)` — если контент уже в кэше, не перезапрашивать. TanStack Query с ключом `['chapter-content', id]` решает кэширование автоматически.

**Побочный эффект:** нужно аккуратно разделить тип `Chapter` на `ChapterMeta` (без контента) и `ChapterFull` (с контентом), чтобы TypeScript это контролировал.

## Задачи — от критичного к некритичному

### 1. Уведомление Роскомнадзора ⚠️

**Что это:** по закону ФЗ-152 любой сайт, собирающий данные пользователей (email, имя), обязан зарегистрироваться как оператор персональных данных. Штраф за отсутствие — ~5 000 ₽, но при проверке могут быть последствия серьёзнее.

**Что сделать:** зайти на pd.rkn.gov.ru, заполнить форму (~30 минут). Указать: оператор — физлицо (ФИО), цель обработки — регистрация и авторизация пользователей, категории данных — email.

### 2. GitHub Flow — защита прода

**Что это:** сейчас все коммиты идут напрямую в `main`, который сразу деплоится на прод. Один сломанный коммит = сломанный прод для реальных пользователей. После запуска это неприемлемо.

**Что сделать:** новые фичи делать в `feature/xxx`-ветках, мержить в `main` только после проверки. Добавить ручную проверку golden path перед каждым мержем: войти → открыть книгу → написать текст → убедиться, что всё работает.

### 3. ЮKassa — платёжный провайдер

**Что это:** без платёжной системы нет монетизации. ЮKassa поддерживает самозанятых (4% с физлиц), работает без ИП. Нужна Edge Function для приёма вебхуков от ЮKassa и обновления поля `plan` в таблице `profiles`.

**Что сделать:** зарегистрироваться в ЮKassa, получить `shop_id` и `secret_key` → создать Supabase Edge Function `yukassa-webhook` → при успешной оплате обновлять `profiles.plan = 'pro'` и `profiles.plan_expires_at`.

### 4. Оферта, акцепт и подтверждение оплаты (при запуске ЮKassa)

**Что это:** три юридических требования при приёме денег онлайн. Без них штраф 3 000–4 000 ₽ за каждое нарушение.

- **Оферта** — страница `/offer`: что продаётся, цена, как отменить подписку.
- **Акцепт** — кнопка «Оплатить» должна содержать текст «Нажимая, вы соглашаетесь с условиями оферты» со ссылкой.
- **Подтверждение заказа** — после оплаты отправить email с номером транзакции (через Supabase Edge Function + Resend/Postmark).

### 7. Горячие клавиши — power-user режим

**Что это:** TipTap уже обрабатывает стандартные шорткаты (`Ctrl+B`, `Ctrl+I` и т.д.), но нет горячих клавиш для навигации по приложению — переключение глав, смена режима, фокус. Это первое что проверяют опытные авторы после установки.

**Почему сейчас:** минимальное усилие, максимальная заметность. Power-user авторы это рассказывают другим. Не требует БД или миграций.

**Что сделать:** добавить глобальный `keydown`-обработчик в `EditorHybrid.tsx` (через `useEffect`). Целевой набор:

Сохранять список шорткатов в отдельном файле `src/lib/shortcuts.ts` — чтобы позже можно было сделать настраиваемые биндинги. В настройках (`SettingsModal`) добавить вкладку «Горячие клавиши» с таблицей-справочником (без кастомизации на первом этапе).

### 10. Форматирование при экспорте — красные строки и читаемость

**Что это:** при экспорте в DOCX/EPUB/FB2 пропадают красные строки (абзацные отступы). В Word открывается сплошной текст без привычного форматирования прозы. Для экспорта художественного текста это критично.

**Что сделать:**

- **DOCX:** у каждого параграфа устанавливать `ParagraphProperties` → `indent: { firstLine: 720 }` (720 = 0.5 дюйма, стандарт для прозы). Альтернатива по желанию автора: межабзацный отступ (`spacing.before: 200`) — оба варианта должны быть в опциях.
- **EPUB/FB2:** `text-indent: 1.5em` через CSS/стиль параграфа.
- **Опция экспорта:** добавить переключатель «Стиль абзацев» с вариантами «Красная строка» / «Интервал между абзацами» — сохранять в `localStorage`.
- **Заметки как примечания автора:** если «Сноски» выключены, заметки вставляются блоком «Примечания» в конце каждой главы, курсивом, с заголовком «Примечание автора».

### 14. Sticky-заголовок «Главы» в сайдбаре

### 15. Привязка заметок к главам и фрагментам текста

**Что это:** все заметки сейчас «плавающие» — нет привязки к конкретной главе или месту в тексте. В сайдбаре редактора нет фильтрации по главе. Для работы с длинным текстом это создаёт хаос — невозможно найти заметку к конкретной сцене.

**Схема:**

- Заметка получает опциональное поле `chapter_id` (привязана к главе) и `anchor_text text` (выделенный фрагмент как текстовый якорь — не позиция, т.к. текст меняется).
- Заметки без `chapter_id` — **общие**, видны только на странице «Заметки» в разделе «Общие».
- Сайдбар заметок в редакторе показывает **только заметки текущей главы** (`chapter_id = current`).
- При создании заметки из редактора — `chapter_id` проставляется автоматически.
- На странице «Заметки» — фильтр: «Все» / «По главам» / «Общие».

**Что сделать:**
1. Миграция: `ALTER TABLE notes ADD COLUMN chapter_id uuid REFERENCES chapters(id) ON DELETE SET NULL`.
2. `NotesPanel` (`src/components/NotesPanel.tsx`): фильтровать по `chapter_id = activeChapterId`.
3. Страница «Заметки»: добавить вкладки / фильтр.
4. Кнопка «Новая заметка» в редакторе: автоматически ставить `chapter_id`.

### 16. Хронология — змейка при переполнении

**Что это:** при большом числе событий хронология уходит горизонтально за экран — нет ограничения ширины, появляется горизонтальный скролл. При 20+ событиях это неудобно.

**Варианты:**

- **Змейка (snake layout):** события идут слева направо, затем переходят на новую строку справа налево — как стрип комикса. Выглядит органично для нарративных инструментов.
- **Многострочная лента:** просто `flex-wrap: wrap` — события переносятся на следующую строку.
- **Вертикальная хронология:** переориентировать ось на вертикальную (список с временными метками слева).

**Рекомендация:** провести ресёрч похожих инструментов (Aeon Timeline, Scrivener, Campfire). Скорее всего — вертикальная ось с горизонтальными «дорожками» для разных персонажей/линий сюжета. Змейка — визуально интересна, но сложна в реализации и фильтрации.

**Что сделать сейчас (минимум):** ограничить контейнер `max-width: 100%` + `overflow-x: auto` + добавить кнопку «свернуть/развернуть» для каждого события, чтобы длинные описания не растягивали карточки.

### 17. Графическая карта мира — переосмысление UX

**Что это:** раздел «Карта» (`Map.tsx`) сейчас показывает локации списком. Функционал создания карты неудобный — неочевидно как добавить локацию, как создать связи, как ориентироваться. Для фэнтези и sci-fi авторов нужна визуальная интерактивная карта.

**Проблемы текущего UX (зафиксировано при тестировании):** неочевидный способ добавления локаций; нет визуальной карты (только список); нет drag & drop для расстановки мест на холсте.

Нужны: холст с zoom/pan, метки/локации с координатами `x/y`, связи-дороги между локациями, загрузка своего изображения карты как фона.

### 21. История версий главы — snapshots + restore

**Что это:** сейчас нет истории изменений. Если автор случайно удалил текст и не нажал Ctrl+Z вовремя — всё потеряно. Autosave перезаписывает без версий. Для авторов, которые пишут роман месяцами, это огромная боль.

**Почему не делать наивно:** если снимать версию каждые 700 мс (как autosave), таблица `chapter_versions` за месяц активной работы превратится в 500 000+ строк на одного автора. Нужна стратегия с умеренной частотой.

**Минимально жизнеспособная версия (делать первой):**

- Снимок при закрытии вкладки / навигации прочь от главы (`beforeunload` + `useEffect` cleanup)
- Снимок раз в час во время активной работы (throttle по таймеру)
- Хранить максимум **50 версий** на главу — при превышении удалять самые старые

Это покрывает 90% боли («я закрыл вкладку и потерял 2 часа работы») почти без нагрузки на БД.

**Схема:**

```sql
create table chapter_versions (
  id uuid primary key default gen_random_uuid(),
  chapter_id uuid references chapters(id) on delete cascade,
  content text not null,
  word_count integer,
  created_at timestamptz default now()
);
-- RLS: через book_id → user_id
create index on chapter_versions (chapter_id, created_at desc);
```

**UI:** отдельная панель «История» в правой панели редактора. Список снимков с датой и кол-вом слов. Клик → предпросмотр в readonly. Кнопка «Восстановить» → заменяет текущий контент (с подтверждением через `ConfirmDialog`).

**Что сделать потом:** после 10+ пользователей — спросить, нужны ли именованные снимки («финальная версия главы 3») и экспорт версий. Если да — добавить поле `label text` в таблицу.

### 28. Автосвязь персонажей и глав

**Что это:** сейчас привязка персонажа к главе — ручная (через `chapter_characters`). Идея — автоматически определять, в каком тексте упоминается персонаж, и строить на этом аналитику: «в каких главах появляется Иван», «timeline персонажа», «связанные сцены».

**Почему не сейчас:** реализовывать только после того, как 20–30 авторов начнут жаловаться на неудобство ручной привязки — это сигнал реальной боли. До этого — это фича для воображаемых пользователей.

**Сложности, которые надо решить заранее:**
- **Морфология:** «Иван», «Ивана», «Ивану», «Ивановым» — одно лицо. Простой `indexOf` не работает. Нужен либо список псевдонимов на карточке персонажа, либо интеграция с морфологической библиотекой (pymorphy2 через Edge Function, или `@vitalets/google-translate-api` как обходной путь — плохо).
- **Производительность:** парсить TipTap JSON на каждый autosave (700 мс) нельзя. Сканировать только при сохранении снимка (раз в час) или по кнопке «Обновить связи».
- **False positive:** персонаж «Лес» будет найден в каждом втором предложении.

**Минимальная реализация (когда придёт время):**

1. На карточке персонажа добавить поле `aliases text[]` — список имён для поиска: `["Иван", "Ваня", "Иванов"]`.
2. При сохранении снимка версии — пробегаться по `aliases` через `chapter.content` (plain text из TipTap JSON), собирать совпадения.
3. Записывать в `chapter_characters` автоматически найденные связи с флагом `auto_detected boolean`.
4. В карточке персонажа — вкладка «Главы» со списком: ручные связи + автонайденные (с пометкой).
5. В хронологии — фильтр по персонажу показывает главы, где он упоминается.

**Не делать на первом этапе:** NLP, семантический поиск, граф связей — это отдельный продукт.

### 29. Двухсторонние и асимметричные связи персонажей

**Что это:** если в карточке персонажа А указана связь с Б, у Б ничего не появляется — связи односторонние. Для простых симметричных отношений (муж–жена, брат–сестра) это создаёт дублирование работы. Но есть асимметричные связи: для Дэмиена — Баки «питомец», для Баки (если у него есть карточка) — Дэмиен «хозяин» / «компаньон по охоте».

**Что сделать:**

1. **Схема связей:** таблица `character_relationships (id, char_a_id, char_b_id, label_a text, label_b text, book_id)`. `label_a` — как A видит B («питомец»), `label_b` — как B видит A («компаньон»). Если `label_b` не заполнено — связь симметричная (один лейбл на обоих).
2. **UI в карточке:** при добавлении связи — поле «Как вы видите их» + опциональное «Как они видят вас». Если второе поле пустое — подставлять тот же лейбл (симметрия).
3. **Автоотображение:** в карточке Б автоматически показывать обратную связь с А с соответствующим `label_b`. Метка «(автоматически)» или «(взаимная связь)».
4. **Стандартные пресеты:** «Отец–сын», «Мать–дочь», «Муж–жена», «Друг–друг» — кликнуть пресет → обе метки заполняются автоматически.
