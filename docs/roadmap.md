### 🔴 Потеря текста при ошибке сети во время автосохранения

**Файл:** `src/pages/Editor.tsx`, функция `flush` (строки 78–93).

**Что происходит:** `pendingPatch.current = null` выставляется **до** `await updateChapter(...)`. Если запрос падает (офлайн, таймаут, 500 от Supabase), патч уже уничтожен — восстановить невозможно. Пользователь видит «Ошибка сохранения», но потерянный текст не вернуть.

```ts
// сейчас — НЕПРАВИЛЬНО:
pendingPatch.current = null;   // ← очищается до запроса
await updateChapter(id, patch) // ← если упало, patch потерян
```

**Фикс:**
```ts
// правильно — очищать только после успеха:
const patch = pendingPatch.current;
pendingPatch.current = null;
try {
  await updateChapter(id, patch);
} catch {
  pendingPatch.current = patch; // ← вернуть патч обратно
  setSaveState('error');
  // + запланировать retry через 3–5 сек
}
```

Дополнительно: показывать постоянный баннер при `saveState === 'error'` (не просто текст в статусбаре) — чтобы пользователь знал, что последнее изменение не сохранено.

### 🔴 Потеря последних изменений при закрытии вкладки

**Файл:** `src/pages/Editor.tsx`.

**Что происходит:** автосохранение работает с debounce 700 мс. Если пользователь закрыл вкладку в течение этих 700 мс после последнего нажатия клавиши — изменения потеряны. `flush` при unmount (`useEffect` cleanup) не успевает выполниться асинхронно при закрытии браузера.

**Фикс:** добавить `beforeunload`-обработчик, который синхронно вызывает `navigator.sendBeacon` с патчем (единственный способ гарантированно отправить запрос при закрытии вкладки):

```ts
useEffect(() => {
  const handler = () => {
    const patch = pendingPatch.current;
    const id = targetIdRef.current;
    if (!patch || !id) return;
    // sendBeacon — fire-and-forget, браузер не блокирует закрытие
    navigator.sendBeacon(
      `/api/chapters/${id}`,
      JSON.stringify(patch)
    );
  };
  window.addEventListener('beforeunload', handler);
  return () => window.removeEventListener('beforeunload', handler);
}, []);
```

Для этого нужен простой API-эндпоинт (Supabase Edge Function `PATCH /chapters/:id`) — прямой вызов Supabase JS SDK из `sendBeacon` не работает.

Альтернатива проще: перед закрытием делать `flush()` синхронно с `keepalive: true` через `fetch`. Но это работает только если запрос < 64 КБ (для главы — обычно ок).

### 🔴 Загрузка полного контента всех глав при открытии книги

**Файл:** `src/lib/chapters.ts`, функция `listChapters` (строка 43).

**Что происходит:** `select('*')` грузит поле `content` (весь HTML текст) для **каждой** главы при каждом открытии редактора. Сайдбар показывает только `title` и `status` — контент не нужен до тех пор, пока пользователь не кликнул на главу. Для книги 100 глав × 3 000 слов ≈ 600–800 КБ лишнего трафика при каждом открытии.

**Фикс:** разделить на два запроса.

```ts
// 1. Список глав — только метаданные (для сайдбара):
export async function listChapters(bookId: string) {
  return supabase
    .from('chapters')
    .select('id, title, position, status, words, created_at, updated_at')
    .eq('book_id', bookId)
    .order('position', { ascending: true });
}

// 2. Контент — только при выборе главы:
export async function getChapterContent(id: string) {
  return supabase
    .from('chapters')
    .select('id, content')
    .eq('id', id)
    .single();
}
```

В `Editor.tsx`: хранить `content` отдельно от списка глав. При `selectChapter(id)` — если контент уже в кэше, не перезапрашивать. TanStack Query с ключом `['chapter-content', id]` решает кэширование автоматически.

**Побочный эффект:** нужно аккуратно разделить тип `Chapter` на `ChapterMeta` (без контента) и `ChapterFull` (с контентом), чтобы TypeScript это контролировал.

**Что это:** по закону ФЗ-152 любой сайт, собирающий данные пользователей (email, имя), обязан зарегистрироваться как оператор персональных данных. Штраф за отсутствие — ~5 000 ₽, но при проверке могут быть последствия серьёзнее.

### 21. История версий главы — snapshots + restore

**Что это:** сейчас нет истории изменений. Если автор случайно удалил текст и не нажал Ctrl+Z вовремя — всё потеряно. Autosave перезаписывает без версий. Для авторов, которые пишут роман месяцами, это огромная боль.

**Почему не делать наивно:** если снимать версию каждые 700 мс (как autosave), таблица `chapter_versions` за месяц активной работы превратится в 500 000+ строк на одного автора. Нужна стратегия с умеренной частотой.

**Минимально жизнеспособная версия (делать первой):**

- Снимок при закрытии вкладки / навигации прочь от главы (`beforeunload` + `useEffect` cleanup)
- Снимок раз в час во время активной работы (throttle по таймеру)
- Хранить максимум **50 версий** на главу — при превышении удалять самые старые

Это покрывает 90% боли («я закрыл вкладку и потерял 2 часа работы») почти без нагрузки на БД.

**Схема:**

```sql
create table chapter_versions (
  id uuid primary key default gen_random_uuid(),
  chapter_id uuid references chapters(id) on delete cascade,
  content text not null,
  word_count integer,
  created_at timestamptz default now()
);
-- RLS: через book_id → user_id
create index on chapter_versions (chapter_id, created_at desc);
```

**UI:** отдельная панель «История» в правой панели редактора. Список снимков с датой и кол-вом слов. Клик → предпросмотр в readonly. Кнопка «Восстановить» → заменяет текущий контент (с подтверждением через `ConfirmDialog`).

**Что сделать потом:** после 10+ пользователей — спросить, нужны ли именованные снимки («финальная версия главы 3») и экспорт версий. Если да — добавить поле `label text` в таблицу.

### 28. Автосвязь персонажей и глав

**Что это:** сейчас привязка персонажа к главе — ручная (через `chapter_characters`). Идея — автоматически определять, в каком тексте упоминается персонаж, и строить на этом аналитику: «в каких главах появляется Иван», «timeline персонажа», «связанные сцены».

**Почему не сейчас:** реализовывать только после того, как 20–30 авторов начнут жаловаться на неудобство ручной привязки — это сигнал реальной боли. До этого — это фича для воображаемых пользователей.

**Сложности, которые надо решить заранее:**
- **Морфология:** «Иван», «Ивана», «Ивану», «Ивановым» — одно лицо. Простой `indexOf` не работает. Нужен либо список псевдонимов на карточке персонажа, либо интеграция с морфологической библиотекой (pymorphy2 через Edge Function, или `@vitalets/google-translate-api` как обходной путь — плохо).
- **Производительность:** парсить TipTap JSON на каждый autosave (700 мс) нельзя. Сканировать только при сохранении снимка (раз в час) или по кнопке «Обновить связи».
- **False positive:** персонаж «Лес» будет найден в каждом втором предложении.

**Минимальная реализация (когда придёт время):**

1. На карточке персонажа добавить поле `aliases text[]` — список имён для поиска: `["Иван", "Ваня", "Иванов"]`.
2. При сохранении снимка версии — пробегаться по `aliases` через `chapter.content` (plain text из TipTap JSON), собирать совпадения.
3. Записывать в `chapter_characters` автоматически найденные связи с флагом `auto_detected boolean`.
4. В карточке персонажа — вкладка «Главы» со списком: ручные связи + автонайденные (с пометкой).
5. В хронологии — фильтр по персонажу показывает главы, где он упоминается.

**Не делать на первом этапе:** NLP, семантический поиск, граф связей — это отдельный продукт.
