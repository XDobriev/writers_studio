### 🟡 TipTap: предупреждение о дублировании расширений link и underline

**Файл:** `src/components/RichEditor.tsx`

**Что происходит:** в консоли появляется `[tiptap warn]: Duplicate extension names found: ['link', 'underline']`. Причина — `StarterKit` уже включает эти расширения, а в `extensions: []` они подключены повторно явно.

**Что сделать:** передать в `StarterKit.configure({ link: false, ... })` отключение встроенных версий, оставив только явные с кастомными настройками. Либо убедиться, что `StarterKit` не включает их (зависит от версии).

> 🛠 **Скилл:** `/systematic-debugging` — структурированно проходит по extensions-дереву, исключает race condition между StarterKit и явными расширениями.

## Задачи — от критичного к некритичному

### 1. Уведомление Роскомнадзора ⚠️

**Что это:** по закону ФЗ-152 любой сайт, собирающий данные пользователей (email, имя), обязан зарегистрироваться как оператор персональных данных. Штраф за отсутствие — ~5 000 ₽, но при проверке могут быть последствия серьёзнее.

**Что сделать:** зайти на pd.rkn.gov.ru, заполнить форму (~30 минут). Указать: оператор — физлицо (ФИО), цель обработки — регистрация и авторизация пользователей, категории данных — email.

### 2. GitHub Flow + Playwright CI — защита прода

**Что это:** сейчас все коммиты идут напрямую в `main`, который сразу деплоится на прод. Нет тестов, нет проверки перед деплоем — один сломанный коммит = сломанный прод. После запуска с реальными пользователями это неприемлемо.

**Что сделать — три шага по нарастающей:**

**Шаг 1 — feature-ветки (сейчас, 0 усилий).** Новые фичи делать в `feature/xxx`, мержить в `main` только через Pull Request. Vercel автоматически создаёт preview-URL для каждой ветки — можно проверить до мержа.

**Шаг 2 — Playwright e2e (1–2 часа).** `npm i -D @playwright/test && npx playwright install chromium`. Один файл `e2e/golden-path.spec.ts`: логин → открыть книгу → написать текст → перезагрузить → текст сохранился. Запускать локально перед каждым мержем.

**Шаг 3 — GitHub Actions CI (30 минут после шага 2).** Файл `.github/workflows/ci.yml`: при push в любую ветку запускать `npm run typecheck` + Playwright против Vercel preview URL. Мержить в `main` только после зелёного CI. Vercel умеет отдавать preview URL через официальный GitHub Action.

### 3. ЮKassa — платёжный провайдер

**Что это:** без платёжной системы нет монетизации. ЮKassa поддерживает самозанятых (4% с физлиц), работает без ИП. Нужна Edge Function для приёма вебхуков от ЮKassa и обновления поля `plan` в таблице `profiles`.

**Что сделать:** зарегистрироваться в ЮKassa, получить `shop_id` и `secret_key` → создать Supabase Edge Function `yukassa-webhook` → при успешной оплате обновлять `profiles.plan = 'pro'` и `profiles.plan_expires_at`.

### 4. Оферта, акцепт и подтверждение оплаты (при запуске ЮKassa)

**Что это:** три юридических требования при приёме денег онлайн. Без них штраф 3 000–4 000 ₽ за каждое нарушение.

- **Оферта** — страница `/offer`: что продаётся, цена, как отменить подписку.
- **Акцепт** — кнопка «Оплатить» должна содержать текст «Нажимая, вы соглашаетесь с условиями оферты» со ссылкой.
- **Подтверждение заказа** — после оплаты отправить email с номером транзакции (через Supabase Edge Function + Resend/Postmark).

### 5. Lifetime deal — 50 мест

**Что это:** при публичном анонсе предложить первые 50 мест за 4 900 ₽ (вместо 290 ₽/мес × навсегда). Ограниченность создаёт срочность. После 50 продаж — убрать Lifetime, оставить только месячный/годовой планы.

**Что сделать:** добавить поле `lifetime_slots_remaining integer` в таблицу `settings` (или как env). Показывать счётчик на лендинге и в модалке апгрейда: «осталось X мест». Декрементировать через вебхук ЮKassa при каждой Lifetime-покупке.

### 6. Грандфазеринг — заморозка цены для первых пользователей

**Что это:** первые ~100–200 пользователей на месячном плане должны навсегда платить 290 ₽, даже когда цена поднимется до 390 ₽. Это стимул для ранней регистрации и обязательство перед аудиторией.

**Что сделать:** добавить поле `grandfathered boolean default false` в таблицу `profiles`. Выставлять `true` при создании подписки в Фазе 1. Биллинговая логика: если `grandfathered = true` → списывать 290 ₽, иначе → актуальная цена.

### 7. Горячие клавиши — power-user режим

**Что это:** TipTap уже обрабатывает стандартные шорткаты (`Ctrl+B`, `Ctrl+I` и т.д.), но нет горячих клавиш для навигации по приложению — переключение глав, смена режима, фокус. Это первое что проверяют опытные авторы после установки.

**Почему сейчас:** минимальное усилие, максимальная заметность. Power-user авторы это рассказывают другим. Не требует БД или миграций.

**Что сделать:** добавить глобальный `keydown`-обработчик в `EditorHybrid.tsx` (через `useEffect`). Целевой набор:

| Клавиша | Действие |
|---|---|
| `Ctrl+Enter` | Создать новую главу |
| `Ctrl+Shift+[` | Предыдущая глава |
| `Ctrl+Shift+]` | Следующая глава |
| `Ctrl+Shift+F` | Переключить Focus-режим |
| `Ctrl+S` | Принудительное сохранение (flush debounce) |
| `Ctrl+Shift+N` | Новая заметка на полях |

Сохранять список шорткатов в отдельном файле `src/lib/shortcuts.ts` — чтобы позже можно было сделать настраиваемые биндинги. В настройках (`SettingsModal`) добавить вкладку «Горячие клавиши» с таблицей-справочником (без кастомизации на первом этапе).

### 8. Соавторство — приглашение редактора

**Что это:** владелец книги может пригласить другого пользователя редактировать. Нужна таблица `book_collaborators` с ролями `editor | viewer`.

**Что сделать:** миграция — таблица `book_collaborators (book_id, user_id, role, invited_by, created_at)`. Владелец вводит email → создаётся pending-запись → пользователь получает email с ссылкой → принимает приглашение. RLS: `auth.uid() = user_id OR EXISTS (SELECT 1 FROM book_collaborators WHERE book_id = ... AND user_id = auth.uid())`.

### 10. Форматирование при экспорте — красные строки и читаемость

**Что это:** при экспорте в DOCX/EPUB/FB2 пропадают красные строки (абзацные отступы). В Word открывается сплошной текст без привычного форматирования прозы. Для экспорта художественного текста это критично.

**Что сделать:**

- **DOCX:** у каждого параграфа устанавливать `ParagraphProperties` → `indent: { firstLine: 720 }` (720 = 0.5 дюйма, стандарт для прозы). Альтернатива по желанию автора: межабзацный отступ (`spacing.before: 200`) — оба варианта должны быть в опциях.
- **EPUB/FB2:** `text-indent: 1.5em` через CSS/стиль параграфа.
- **Опция экспорта:** добавить переключатель «Стиль абзацев» с вариантами «Красная строка» / «Интервал между абзацами» — сохранять в `localStorage`.
- **Заметки как примечания автора:** если «Сноски» выключены, заметки вставляются блоком «Примечания» в конце каждой главы, курсивом, с заголовком «Примечание автора».

### 13. Автор при экспорте из профиля

**Что это:** поле «Автор» в диалоге экспорта пустое по умолчанию. Пользователю каждый раз нужно вводить своё имя вручную.

**Что сделать:** при открытии диалога экспорта подставлять `profile.display_name` (или `profile.full_name`) как значение по умолчанию. Поле остаётся редактируемым — автор может поменять псевдоним перед конкретным экспортом. Значение не сохранять между сессиями (каждый раз брать из профиля свежее).

### 15. Хронология — змейка при переполнении

**Что это:** при большом числе событий хронология уходит горизонтально за экран — нет ограничения ширины, появляется горизонтальный скролл. При 20+ событиях это неудобно.

**Варианты:**

- **Змейка (snake layout):** события идут слева направо, затем переходят на новую строку справа налево — как стрип комикса. Выглядит органично для нарративных инструментов.
- **Многострочная лента:** просто `flex-wrap: wrap` — события переносятся на следующую строку.
- **Вертикальная хронология:** переориентировать ось на вертикальную (список с временными метками слева).

**Рекомендация:** провести ресёрч похожих инструментов (Aeon Timeline, Scrivener, Campfire). Скорее всего — вертикальная ось с горизонтальными «дорожками» для разных персонажей/линий сюжета. Змейка — визуально интересна, но сложна в реализации и фильтрации.

**Что сделать сейчас (минимум):** ограничить контейнер `max-width: 100%` + `overflow-x: auto` + добавить кнопку «свернуть/развернуть» для каждого события, чтобы длинные описания не растягивали карточки.

> 🛠 **Скилл:** `/impeccable` — полезен при выборе между змейкой / вертикальной осью / wrap; может отрисовать mockup каждого варианта до реализации.

### 25. Расширенная проверка орфографии + пользовательский словарь

**Что это:** сейчас проверка орфографии — браузерная (`spellcheck`). Браузер не знает авторских имён, выдуманных топонимов, терминов фэнтези-мира — подчёркивает их красным. LanguageTool API умеет стилистику, пунктуацию, согласование — полноценный аналог Grammarly на русском.

**Проблемы зафиксированные при тестировании:**
1. При исправлении одного слова мигают подчёркивания у остальных (см. баг 🟡 выше).
2. Нет возможности добавить слово в словарь — «Дэмиен», «Арвен», «Серебряный Лес» будут подчёркиваться вечно.

**Что сделать (по приоритету):**
1. **Пользовательский словарь (сначала):** в контекстном меню подчёркнутого слова добавить пункт «Добавить в мой словарь». Хранить как `user_dictionary text[]` в `profiles`. При загрузке редактора — передавать словарь в TipTap, игнорировать эти слова при проверке.
2. **LanguageTool (потом, Pro-план):** TipTap-расширение поверх LanguageTool API. Подсветка ошибок → контекстное меню с исправлениями. Исправить мерцание через оптимизацию декораций (см. баг 🟡).

> 🛠 **Скилл:** `/systematic-debugging` — для пользовательского словаря в TipTap нужно корректно расширить схему; скилл помогает не сломать существующий spellcheck-flow.

### 28. Автосвязь персонажей и глав

**Что это:** сейчас привязка персонажа к главе — ручная (через `chapter_characters`). Идея — автоматически определять, в каком тексте упоминается персонаж, и строить на этом аналитику: «в каких главах появляется Иван», «timeline персонажа», «связанные сцены».

**Почему не сейчас:** реализовывать только после того, как 20–30 авторов начнут жаловаться на неудобство ручной привязки — это сигнал реальной боли. До этого — это фича для воображаемых пользователей.

**Сложности, которые надо решить заранее:**
- **Морфология:** «Иван», «Ивана», «Ивану», «Ивановым» — одно лицо. Простой `indexOf` не работает. Нужен либо список псевдонимов на карточке персонажа, либо интеграция с морфологической библиотекой (pymorphy2 через Edge Function, или `@vitalets/google-translate-api` как обходной путь — плохо).
- **Производительность:** парсить TipTap JSON на каждый autosave (700 мс) нельзя. Сканировать только при сохранении снимка (раз в час) или по кнопке «Обновить связи».
- **False positive:** персонаж «Лес» будет найден в каждом втором предложении.

**Минимальная реализация (когда придёт время):**

1. На карточке персонажа добавить поле `aliases text[]` — список имён для поиска: `["Иван", "Ваня", "Иванов"]`.
2. При сохранении снимка версии — пробегаться по `aliases` через `chapter.content` (plain text из TipTap JSON), собирать совпадения.
3. Записывать в `chapter_characters` автоматически найденные связи с флагом `auto_detected boolean`.
4. В карточке персонажа — вкладка «Главы» со списком: ручные связи + автонайденные (с пометкой).
5. В хронологии — фильтр по персонажу показывает главы, где он упоминается.

**Не делать на первом этапе:** NLP, семантический поиск, граф связей — это отдельный продукт.

### 29. Двухсторонние и асимметричные связи персонажей

**Что это:** если в карточке персонажа А указана связь с Б, у Б ничего не появляется — связи односторонние. Для простых симметричных отношений (муж–жена, брат–сестра) это создаёт дублирование работы. Но есть асимметричные связи: для Дэмиена — Баки «питомец», для Баки (если у него есть карточка) — Дэмиен «хозяин» / «компаньон по охоте».

**Что сделать:**

1. **Схема связей:** таблица `character_relationships (id, char_a_id, char_b_id, label_a text, label_b text, book_id)`. `label_a` — как A видит B («питомец»), `label_b` — как B видит A («компаньон»). Если `label_b` не заполнено — связь симметричная (один лейбл на обоих).
2. **UI в карточке:** при добавлении связи — поле «Как вы видите их» + опциональное «Как они видят вас». Если второе поле пустое — подставлять тот же лейбл (симметрия).
3. **Автоотображение:** в карточке Б автоматически показывать обратную связь с А с соответствующим `label_b`. Метка «(автоматически)» или «(взаимная связь)».
