## Задачи — от критичного к некритичному

### 1. Уведомление Роскомнадзора ⚠️

**Что это:** по закону ФЗ-152 любой сайт, собирающий данные пользователей (email, имя), обязан зарегистрироваться как оператор персональных данных. Штраф за отсутствие — ~5 000 ₽, но при проверке могут быть последствия серьёзнее.

**Что сделать:** зайти на pd.rkn.gov.ru, заполнить форму (~30 минут). Указать: оператор — физлицо (ФИО), цель обработки — регистрация и авторизация пользователей, категории данных — email.

### 2. Персонажи — контент сайдбара под навигацией

**Что это:** сайдбар на странице Персонажей сейчас содержит только навигацию и пустую область. Во всех остальных разделах под навигацией есть полезный контент (главы в Манускрипте/Заметках/Структуре, фильтры в Доске, события в Хронологии). Нужно решить, что показывать в сайдбаре Персонажей: список персонажей для быстрого перехода, фильтры по роли, или статистику.

**Варианты:**
- Список имён персонажей (быстрый доступ, как главы в манускрипте)
- Фильтры по роли (дубликат фильтров из тулбара, но доступнее)
- Минимально — оставить пустым и сосредоточить управление в главной области

### 3. Логика кнопки «Апгрейд до Pro»

**Что это:** кнопка уже присутствует в сайдбаре (блок «Подписка»), но за ней нет никакой логики. Нужно продумать, что происходит при клике: модальное окно с описанием плана и ценой, редирект на страницу оплаты, или inline-форма? Какие фичи разблокирует Pro? Как выглядит состояние «уже Pro» (кнопка исчезает / показывает дату окончания)?

**Что продумать:**
- Перечень ограничений Free-плана и привилегий Pro (1 книга vs. безлимит, экспорт, etc.)
- UX флоу: клик → что видит пользователь → как переходит к оплате
- Состояние кнопки после апгрейда (заменить на «Pro до [дата]» или убрать)
- Связь с §3 ЮKassa: что именно вызывает кнопка после подключения платёжки

### 3. ЮKassa — платёжный провайдер

**Что это:** без платёжной системы нет монетизации. ЮKassa поддерживает самозанятых (4% с физлиц), работает без ИП. Нужна Edge Function для приёма вебхуков от ЮKassa и обновления поля `plan` в таблице `profiles`.

**Что сделать:** зарегистрироваться в ЮKassa, получить `shop_id` и `secret_key` → создать Supabase Edge Function `yukassa-webhook` → при успешной оплате обновлять `profiles.plan = 'pro'` и `profiles.plan_expires_at`. При регистрации включить партнёрскую интеграцию с ФНС — чеки для самозанятых формируются и отправляются клиентам автоматически, бесплатно.

### 4. Оферта, акцепт и подтверждение оплаты (при запуске ЮKassa)

**Что это:** три юридических требования при приёме денег онлайн. Без них штраф 3 000–4 000 ₽ за каждое нарушение.

- **Оферта** — страница `/offer`: что продаётся, цена, как отменить подписку.
- **Акцепт** — кнопка «Оплатить» должна содержать текст «Нажимая, вы соглашаетесь с условиями оферты» со ссылкой.
- **Подтверждение заказа** — после оплаты отправить email с номером транзакции (через Supabase Edge Function + Resend/Postmark).

### 5. Lifetime deal — 50 мест

**Что это:** при публичном анонсе предложить первые 50 мест за 4 900 ₽ (вместо 290 ₽/мес × навсегда). Ограниченность создаёт срочность. После 50 продаж — убрать Lifetime, оставить только месячный/годовой планы.

**Что сделать:** добавить поле `lifetime_slots_remaining integer` в таблицу `settings` (или как env). Показывать счётчик на лендинге и в модалке апгрейда: «осталось X мест». Декрементировать через вебхук ЮKassa при каждой Lifetime-покупке.

### 6. Грандфазеринг — заморозка цены для первых пользователей

**Что это:** первые ~100–200 пользователей на месячном плане должны навсегда платить 290 ₽, даже когда цена поднимется до 390 ₽. Это стимул для ранней регистрации и обязательство перед аудиторией.

**Что сделать:** добавить поле `grandfathered boolean default false` в таблицу `profiles`. Выставлять `true` при создании подписки в Фазе 1. Биллинговая логика: если `grandfathered = true` → списывать 290 ₽, иначе → актуальная цена.

### 7. Соавторство — приглашение редактора

**Что это:** владелец книги может пригласить другого пользователя редактировать. Нужна таблица `book_collaborators` с ролями `editor | viewer`.

**Что сделать:** миграция — таблица `book_collaborators (book_id, user_id, role, invited_by, created_at)`. Владелец вводит email → создаётся pending-запись → пользователь получает email с ссылкой → принимает приглашение. RLS: `auth.uid() = user_id OR EXISTS (SELECT 1 FROM book_collaborators WHERE book_id = ... AND user_id = auth.uid())`.

### 8. Аналитика онбординга в БД

**Что это:** флаг «пользователь прошёл онбординг» сейчас в `localStorage`. При смене браузера или устройства — онбординг показывается снова. При 50+ пользователях нельзя анализировать воронку.

**Что сделать:** добавить `onboarded_at timestamp` в таблицу `profiles`. При завершении онбординга — записывать дату в БД. `localStorage` оставить как кэш для быстрой проверки.

### 10. Несогласованный useCallback в редакторе

**Что это:** в `Editor.tsx` все обработчики обёрнуты в `useCallback`. В `RichEditor.tsx` функции `applyColor`, `runFmt`, `applySuggestion` — обычные функции. Это не баг, но стиль непоследователен и может вызывать лишние ре-рендеры.

**Что сделать:** при следующем касании `RichEditor.tsx` обернуть эти три функции в `useCallback`.

### 11. Расширенная проверка орфографии + пользовательский словарь

**Что это:** сейчас проверка орфографии — браузерная (`spellcheck`). Браузер не знает авторских имён, выдуманных топонимов, терминов фэнтези-мира — подчёркивает их красным. LanguageTool API умеет стилистику, пунктуацию, согласование — полноценный аналог Grammarly на русском.

**Проблемы зафиксированные при тестировании:**
1. ~~При исправлении одного слова мигают подчёркивания у остальных~~ — ✅ закрыто, точечное удаление декораций.
2. Нет возможности добавить слово в словарь — «Дэмиен», «Арвен», «Серебряный Лес» будут подчёркиваться вечно.

**Что сделать (по приоритету):**
1. **Пользовательский словарь:** в контекстном меню подчёркнутого слова добавить пункт «Добавить в мой словарь». Хранить как `user_dictionary text[]` в `profiles`. При загрузке редактора — передавать словарь в TipTap, игнорировать эти слова при проверке.
2. **LanguageTool (потом, Pro-план):** TipTap-расширение поверх LanguageTool API. Подсветка ошибок → контекстное меню с исправлениями.

> 🛠 **Скилл:** `/systematic-debugging` — для пользовательского словаря в TipTap нужно корректно расширить схему; скилл помогает не сломать существующий spellcheck-flow.

### 11. Соавторство — real-time редактирование

**Что это:** два пользователя редактируют одну главу одновременно, видят курсоры друг друга. Самая сложная фича соавторства — требует Y.js + TipTap Collaboration Extension.

**Что сделать:** реализовывать не раньше 100 платящих пользователей. Варианты бэкенда: Supabase Realtime с Y.js, Hocuspocus на Fly.io/Timeweb. TipTap v3 поддерживает Y.js нативно.

### 12. Автосвязь персонажей и глав

**Что это:** сейчас привязка персонажа к главе — ручная (через `chapter_characters`). Идея — автоматически определять, в каком тексте упоминается персонаж, и строить на этом аналитику: «в каких главах появляется Иван», «timeline персонажа», «связанные сцены».

**Почему не сейчас:** реализовывать только после того, как 20–30 авторов начнут жаловаться на неудобство ручной привязки — это сигнал реальной боли. До этого — это фича для воображаемых пользователей.

**Сложности, которые надо решить заранее:**
- **Морфология:** «Иван», «Ивана», «Ивану», «Ивановым» — одно лицо. Простой `indexOf` не работает. Нужен либо список псевдонимов на карточке персонажа, либо интеграция с морфологической библиотекой (pymorphy2 через Edge Function, или `@vitalets/google-translate-api` как обходной путь — плохо).
- **Производительность:** парсить TipTap JSON на каждый autosave (700 мс) нельзя. Сканировать только при сохранении снимка (раз в час) или по кнопке «Обновить связи».
- **False positive:** персонаж «Лес» будет найден в каждом втором предложении.

**Минимальная реализация (когда придёт время):**

1. На карточке персонажа добавить поле `aliases text[]` — список имён для поиска: `["Иван", "Ваня", "Иванов"]`.
2. При сохранении снимка версии — пробегаться по `aliases` через `chapter.content` (plain text из TipTap JSON), собирать совпадения.
3. Записывать в `chapter_characters` автоматически найденные связи с флагом `auto_detected boolean`.
4. В карточке персонажа — вкладка «Главы» со списком: ручные связи + автонайденные (с пометкой).
5. В хронологии — фильтр по персонажу показывает главы, где он упоминается.

**Не делать на первом этапе:** NLP, семантический поиск, граф связей — это отдельный продукт.

### 13. Двухсторонние и асимметричные связи персонажей

**Что это:** если в карточке персонажа А указана связь с Б, у Б ничего не появляется — связи односторонние. Для простых симметричных отношений (муж–жена, брат–сестра) это создаёт дублирование работы. Но есть асимметричные связи: для Дэмиена — Баки «питомец», для Баки (если у него есть карточка) — Дэмиен «хозяин» / «компаньон по охоте».

**Что сделать:**

1. **Схема связей:** таблица `character_relationships (id, char_a_id, char_b_id, label_a text, label_b text, book_id)`. `label_a` — как A видит B («питомец»), `label_b` — как B видит A («компаньон»). Если `label_b` не заполнено — связь симметричная (один лейбл на обоих).
2. **UI в карточке:** при добавлении связи — поле «Как вы видите их» + опциональное «Как они видят вас». Если второе поле пустое — подставлять тот же лейбл (симметрия).
3. **Автоотображение:** в карточке Б автоматически показывать обратную связь с А с соответствующим `label_b`. Метка «(автоматически)» или «(взаимная связь)».
4. **Стандартные пресеты:** «Отец–сын», «Мать–дочь», «Муж–жена», «Друг–друг» — кликнуть пресет → обе метки заполняются автоматически.

### 14. Перестановка заметок в режиме «Манускрипт»

**Что это:** в режиме «Манускрипт» заметки отображаются на полях рядом с текстом главы, но их нельзя переставить местами. Порядок заметок внутри главы должен быть управляемым.

**Что сделать:** добавить поле `position integer` в таблицу `notes`. В режиме «Манускрипт» — drag & drop через `@dnd-kit/core` (уже используется для глав). При перетаскивании — обновлять `position` заметок текущей главы в Supabase. В обычном виде заметок — сортировка по `position`.

### 15. Время чтения на дашборде книги

**Что это:** в статусбаре редактора уже считается «≈ 2 мин чтения» для текущей главы. На дашборде книги (`BookDashboard`) нет общего времени чтения всей книги — только общее количество слов.

**Что сделать:** добавить карточку «Время чтения» на дашборд книги. Формула: `sum(words) / 200` (200 слов в минуту — стандарт для художественной прозы). Отображать как «≈ 4 ч 30 мин» (часы + минуты). Рядом можно добавить «≈ X страниц» (250 слов = 1 стандартная страница А4). Данные уже есть — `words` считается для каждой главы.

### 16. Жанры книги — список с кастомным вводом

**Что это:** при создании книги поле «Жанр» — свободный текстовый ввод (или вовсе отсутствует). Нет стандартного набора жанров, каждый автор пишет по-своему («фэнтэзи», «фентези», «фэнтези»). Это мешает будущей фильтрации и тегированию.

**Что сделать:** `<select multiple>` или `<Combobox>` с предустановленными жанрами + возможностью добавить свой. Список жанров:

> Роман · Повесть · Рассказ · Фэнтези · Фэнтези (городское) · Фэнтези (тёмное) · Фэнтези (эпическое) · Фантастика · Детектив · Триллер · Хоррор · Романтика · Историческая проза · Приключения · Young Adult · Мистика · Постапокалипсис · Антиутопия · Лирическая проза · Нон-фикшн · Другое

При выборе «Другое» — появляется текстовое поле. Хранить как `genres text[]` в таблице `books`.

### 17. Консолидация деплоя — только Timeweb

**Что это:** сейчас каждый push в `main` деплоит на **два хоста** одновременно:
- Vercel → `avtorskaya-studiya.vercel.app` (авто, через Vercel Git integration)
- Timeweb VPS → `avtorstudio.com` (GitHub Actions, rsync)

Основным является Timeweb (`avtorstudio.com`). Vercel остался как пассивный дублёр.

**Что сделать:** когда Timeweb докажет стабильность (1-2 недели), отключить production-деплой на Vercel — оставить только preview-деплои для PR. В настройках Vercel: `Settings → Git → Production Branch` — отключить или сменить на отдельную ветку `vercel-preview`.

**Опционально:** раскомментировать Supabase-прокси в [deploy/nginx.conf](../deploy/nginx.conf) — тогда API-запросы к Supabase пойдут через российский сервер, а не напрямую из браузера на EU.

### 30. Git-воркфлоу — ветка `dev` для тестирования перед деплоем

**Что это:** сейчас один бранч `main` → авто-деплой сразу на оба хоста (VPS + Vercel). Нет этапа тестирования перед попаданием в прод.

**Что сделать:**
1. Создать ветку `dev`: `git checkout -b dev && git push -u origin dev`
2. Работать в `dev` → push → Vercel автоматически делает preview-URL (полноценный деплой, реальный HTTPS)
3. Протестировать на preview → merge `dev → main` → VPS + Vercel prod обновляются

**Что не трогать:** GitHub Actions уже настроен на `branches: [main]` — VPS не деплоится с `dev` без изменений. Vercel production branch оставить `main` — тогда Vercel остаётся резервным зеркалом прода.

**Когда делать:** перед публичным запуском, когда ошибки в проде станут дорогостоящими.
