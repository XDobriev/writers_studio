### 5. Retention email-триггеры

**Что это:** автоматические письма, которые возвращают пользователя к работе до того, как он задумается об отмене. Самый высокий ROI retention-инструмент для инструмента писателя.

**Три триггера по приоритету:**

| Триггер | Письмо | Когда |
|---|---|---|
| 7 дней без входа | «[Название книги] ждёт вас» — с именем книги и названием последней главы | UniSender Go, автоматически |
| Воскресенье (активные пользователи) | Недельный отчёт: слов написано, прогресс к цели, серия дней | UniSender Go, еженедельно |
| 14 дней без входа (первые 50 пользователей) | Личное письмо от основателя: «Что мешает писать?» | Вручную |

**Активационный сигнал:** пользователь «активирован» когда создал книгу + написал первую главу + вернулся на второй день. До этой точки — онбординг-цепочка; после — retention-триггеры.

**Что нужно из данных:**
- `last_sign_in_at` уже есть в Supabase Auth
- Название текущей книги: запрос к `books` с `max(updated_at)` для пользователя
- Слова за неделю: агрегат по `chapters.word_count` с фильтром `updated_at >= now() - interval '7 days'`

**Реализация:**
- Cron-задача раз в сутки (Supabase Edge Function + pg_cron) → проверяет `last_sign_in_at` → отправляет через UniSender Go
- Недельный отчёт: отдельная Edge Function по расписанию каждое воскресенье

**Файлы:** новая `supabase/functions/retention-trigger/index.ts`  
**Проверить:** вызвать функцию вручную для тестового аккаунта → письмо приходит с правильным именем книги  
**Deps:** §4 (email-механика), UniSender Go API-ключ в Supabase Vault

### 8. CI/CD — решить роль Vercel перед переходом на self-host

> Решение нужно до §9 (VPS Supabase) — именно при self-host конфигурация Vercel становится критичной (риск разъехавшихся данных).

#### Текущее состояние (после фикса 2026-06-10)
- Пуш в `main` → деплой **одновременно** на Timeweb VPS (GitHub Actions) И на Vercel production.
- **Timeweb** (avtorstudio.com) — основной прод, Supabase через `/sb/` прокси на VPS (обходит RU-throttling).
- **Vercel** (avtorskaya-studiya.vercel.app) — параллельный прод, Supabase **напрямую** на supabase.co, скрыт от поисковиков (`X-Robots-Tag: noindex`).
- Ветка `vercel-preview` больше не прод-ветка Vercel — кандидат на удаление.

#### Ключевое ограничение: Vercel ≠ полноценный failover для РФ
1. **Прямой `supabase.co` throttled в РФ** — Vercel не использует VPS-прокси, поэтому для российских пользователей без VPN данные грузятся медленно/не грузятся.
2. **`*.vercel.app` периодически блокируется в РФ** — ненадёжная точка доступа для россиян.
3. **После §9 (self-host Supabase на VPS)** — VPS `/sb/` будет указывать на локальную базу в РФ, а Vercel (прямой supabase.co) — на осиротевшую Cloud-базу. Два деплоя начнут показывать **разные данные**.

#### Реалистичные роли Vercel (выбрать одну/несколько)
- **A. Failover для зарубежных/VPN-пользователей** — для них прямой supabase.co быстрее VPS-прокси. Узкая аудитория (диаспора, эмигранты).
- **B. Smoke-test сборки** — Vercel на каждый пуш проверяет, что `npm run build` проходит и приложение поднимается. Дешёвая страховка от «сломал прод-сборку». Почти бесплатно, уже работает.
- **C. Staging из ветки `dev`** — main → оба прода; `dev`/PR → Vercel preview для QA до мержа.
- **D. Отключить Vercel** — если §9 (self-host) делает его бесполезным.

#### Решения, которые надо принять
1. Какую роль(и) из A–D берём.
2. Судьба Vercel после §9: переключить на self-hosted Supabase (через публичный доменный прокси) или отключить.
3. Удалить отставшие ветки `vercel-preview` и `dev` (10+ коммитов позади) — или оживить `dev` под staging (вариант C).
4. e2e в `ci.yml`: гонять против Vercel preview URL (реальный деплой) вместо localhost.

### 9. Перенос Supabase на VPS — локализация данных (ФЗ-242) ⚠️

**Когда делать:** при ~20 платящих пользователях или когда Supabase Cloud free tier начнёт кончаться (500 МБ база или 50k MAU) — что наступит раньше. DDoS Timeweb 23.06.2026 подтвердил приоритет: прокси VPS→Cloud создаёт точку отказа, self-hosted убирает её.

**Что это:** с 01.07.2025 первичный сбор и хранение ПД граждан РФ обязан происходить на серверах в России (ФЗ-152, ст. 18.1). Supabase Cloud на AWS eu-central-1 (Франкфурт) — нарушение. Штраф для физлица до 50 000 ₽ + РКН вправе заблокировать сайт.

**Решение:** self-hosted Supabase на Timeweb VPS (Ubuntu 24.04, уже оплачен). Данные физически в РФ — нарушения нет.

**Требования к VPS перед началом:** минимум 4 ГБ RAM (рекомендуется 8 ГБ) и 20 ГБ свободного диска. Проверить: `free -h` и `df -h /`. Если меньше — апгрейдить тариф на Timeweb.

**План нулевого даунтайма:**
1. Установить Docker на VPS: `curl -fsSL https://get.docker.com | sh`
2. Скачать Supabase Docker: `git clone --depth 1 --filter=blob:none --sparse https://github.com/supabase/supabase && cd supabase && git sparse-checkout set docker`
3. Сгенерировать секреты: `sh utils/generate-keys.sh` — **использовать тот же `JWT_SECRET` что в Supabase Cloud** (Dashboard → Settings → API) — иначе все активные сессии пользователей инвалидируются
4. Настроить `.env`: `SUPABASE_PUBLIC_URL=https://avtorstudio.com/sb`, поднять контейнеры на `127.0.0.1:8000` (не на публичный интерфейс)
5. Экспортировать только схему `public` из Cloud: `pg_dump --schema=public --no-privileges --no-owner`
6. Импортировать в self-hosted через `docker exec`
7. Запустить оба варианта параллельно (Cloud продолжает работать)
8. Переключить nginx `proxy_pass /sb/` с Cloud URL на `http://127.0.0.1:8000` → `nginx -s reload` (~0.5 сек переключения, пользователи не почувствуют)
9. Мониторить 24–48 часов → отключить Cloud через неделю
10. Обновить `VITE_SUPABASE_ANON_KEY` в Vercel и `.env` на новый сгенерированный ключ
11. Обновить `site_url` / OAuth redirect URLs (Google, Telegram) в self-hosted дашборде
12. Обновить `Privacy.tsx` раздел 4: убрать «ведём работу по переносу», написать «данные хранятся на серверах в РФ»

**Инструмент управления:** использовать Portainer (GUI для Docker, есть в маркетплейсе Timeweb) вместо CLI — проще для первого раза.

**Файлы:** `~/supabase-project/docker-compose.yml` (создать на VPS), `~/supabase-project/.env` (создать на VPS), `/etc/nginx/sites-available/avtorstudio.com` (обновить proxy_pass), `src/pages/Privacy.tsx` (раздел 4), Vercel env vars (`VITE_SUPABASE_ANON_KEY`)  
**Проверить:** `docker compose ps` → все `healthy` → зайти в приложение → авторизация через email работает → Edge Functions отвечают → `SELECT version()` на self-hosted instance

### §INFRA-1. Объектное хранилище для снимков глав (S3/Blob)

**Когда делать:** при 500+ активных Pro-пользователях или когда база `chapter_versions` превысит 4 ГБ. До этого — преждевременная оптимизация.

**Что это:** сейчас HTML-контент снимков хранится прямо в PostgreSQL (`chapter_versions.content TEXT`). При росте числа Pro-пользователей это дорого: Supabase берёт $0.125/ГБ/мес за БД, тогда как Cloudflare R2 стоит $0.015/ГБ/мес.

**Суть изменения:** вынести `content` из PostgreSQL в объектное хранилище (Cloudflare R2 или Supabase Storage). В таблице `chapter_versions` хранить только метаданные + `storage_key` (путь к файлу). `getVersionContent` становится `fetch` вместо SQL. `pruneVersions` — сначала удаляет файлы, потом строки.

**Файлы:** `src/lib/versions.ts`, `supabase/migrations/` (убрать `content` из таблицы, добавить `storage_key`).

### 🔵 Идеи из Everything Claude Code — `lloredia/everything-claude-code`

Победитель хакатона Anthropic. 81 скилл, 16 агентов, 40+ команд. 90% нерелевантно (мультиязычные/enterprise паттерны), но три идеи стоит адаптировать под проект:

1. **Pre-commit quality hook** — автоматический `typecheck + lint` перед каждым коммитом через `.claude/settings.json` хук. Сейчас проверка ручная или через `/ship`. Хук гарантирует, что сломанный код не попадёт в коммит без явного `--no-verify`.

2. **Verification loop (`/verify`)** — скилл на ~20 строк: последовательно гоняет `typecheck → lint → vitest` и выдаёт сводку pass/fail. Аналог ECC `/verify`, но заточенный под наш стек (Vite + React + Supabase). Полезен при рефакторинге и перед PR.

3. **Continuous learning (инстинкты)** — автоматическое извлечение паттернов из сессий в memory-файлы. Сейчас memory-система ручная (пользователь явно просит запомнить). Идея ECC: после каждой сессии анализировать, какие решения были удачными, и сохранять как «инстинкты» для будущих разговоров. Риск: шум в memory → реализовывать осторожно, с порогом confidence.

**Когда:** п.1 — сразу после §2 (тестирование). п.2 — при первом рефакторинге. п.3 — после 10+ сессий, когда станет ясно какие паттерны повторяются.  
**Не устанавливать целиком:** репо — универсальный швейцарский нож, тянет Go/Python/Java/Swift/Perl/Kotlin правила и enterprise-хуки, которые засоряют контекст.
