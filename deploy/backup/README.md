# Ежедневные копии БД и Storage (L-3)

Цель: до суток потерянных изменений, 14 ежедневных точек, ручное восстановление всего сервиса за рабочий день. Достижение цели подтверждает **учебное восстановление**, не факт успешного запуска скрипта. Установка не входит в обычный деплой фронтенда.

## Что происходит

`backup.py` работает от отдельного Linux-пользователя. Он сверяет список S3-файлов Supabase с `storage.objects`, синхронизирует **только локальную** рабочую копию, проверяет содержимое файлов скачиванием, делает полный логический PostgreSQL-архив (в том числе auth, storage, public и пользовательские схемы), экспортирует роли без паролей и расшифрованные значения Vault, добавляет комплект восстановления. Повторное сравнение Storage после дампа ловит изменения файлов во время копирования. При несовпадении снимок не публикуется — повторить после завершения загрузок. Дамп БД транзакционно согласован; общей транзакции между PostgreSQL и файлами нет.

Снимок содержит `database.dump`, `roles.sql`, `vault.json`, `storage.json`, `storage/`, `recovery/` и `manifest.json` с SHA-256 каждого файла. `restic backup` шифрует, сжимает и дедуплицирует его в Yandex S3. Дамп перед restic не сжимается, чтобы не мешать дедупликации. После загрузки — `restic check`. Весь вывод сторонних команд подавляется: в нём бывают URL с паролями, имена файлов пользователей и чувствительные значения. Скрипт сообщает только этап ошибки.

**На VPS остаётся одна рабочая копия, не 14 архивов.** Нужен диск под текущие файлы, временный дамп и кэш restic; PostgreSQL и файлы пользователей продолжают жить в Supabase. Начальный замер: около 0,49 МиБ строк public/auth/storage и 6,31 МиБ файлов; это не размер готового бэкапа. Перед активацией измерить пик диска и RAM. В systemd установить `MemoryMax` только по измерению, чтобы не оборвать дамп произвольным лимитом. При свободном диске <256 МиБ скрипт не начинает копирование; это предохранитель, а не дисковая квота.

## Подготовка доступа (без секретов в Git или чате)

1. В Yandex Cloud создать отдельный приватный бакет **STANDARD**, без публичного чтения и без автоматического удаления объектов. Завести отдельный service account, выдать `storage.editor` **на этот бакет**, создать статический ключ. Не выдавать роли на всё облако. Создать уведомление о расходах; бюджет — уведомление, не жёсткая остановка оплаты. Контролировать размер всего бакета, включая старые версии/незавершённые multipart-загрузки. 1 ГБ — бесплатный объём, а не максимальная вместимость.
2. Создать случайный пароль restic и сохранить **ещё одну копию вне VPS** в менеджере паролей. Потеря пароля делает все снимки непригодными. Не хранить единственный ключ внутри своего же бэкапа.
3. Получить PostgreSQL connection parameters в Supabase → Connect: прямое подключение с TLS или **session pooler**, не transaction pooler. Пароль БД не менять ради задачи без отдельного решения владельца. Сохранить параметры в `pg_service.conf`, пароль — в `pgpass` (формат libpq, экранировать `:` и `\`). Не передавать connection URL с паролем в командной строке.
4. В Supabase Storage получить отдельные S3 credentials и фактические endpoint/region. Они нужны rclone для чтения **всех бакетов**, не только публичных. Не использовать ключи Yandex для источника.
5. Подготовить восстановительный комплект ниже. Проверить доставку внешнего сигнала о пропущенном запуске (24 часа + допустимая длительность, например 30 часов). Обычный `/sb-health` этого не проверяет. `BACKUP_HEALTHCHECK_URL` — приватный URL сервиса heartbeat с поддержкой `GET <url>` и `GET <url>/fail`; выбрать сервис и проверить уведомления до включения таймера. Сбой доставки сигнала записывается в journal, копия сохраняется.

S3 Object Lock и lifecycle-delete **не включать на рабочем restic-репозитории**: блокировка/внешнее удаление его общих блоков мешают `prune` и могут повредить все снимки. В первой версии ключ на VPS может удалять данные бакета; шифрование не защищает от удаления при компрометации этого ключа. Не заявлять защиту от вымогателей. Дополнительная неизменяемая/append-only копия потребует отдельного решения и теста, не самодельной блокировки restic-файлов.

## Закрытые файлы на VPS

`/etc/avtorstudio-backup` — root-owned, группа `avtorstudio-backup`, режим `0750`. Все файлы с секретами, которые читает процесс, принадлежат `avtorstudio-backup` и имеют `0600`; вложенные каталоги — `0700`. `backup.env` может быть root-owned `0600`: его читает systemd до смены пользователя. На рабочем месте также держать секреты вне checkout.

Файлы:

- `backup.env` — на основе `backup.env.example` с настоящим именем бакета и ключами Yandex. Это формат systemd EnvironmentFile; не запускать `source` на недоверенном файле.
- `restic-password` — только пароль restic и перевод строки.
- `pg_service.conf`, `pgpass` — параметры PostgreSQL, TLS `sslmode=verify-full` с корневым сертификатом Supabase и путь к нему. Для pooler использовать параметры именно из Connect, не угадывать регион/hostname.
- `rclone.conf` — источник Supabase. Endpoint и region взять из Dashboard. Секреты не помещать в `env.example`.

```ini
# pg_service.conf (без пароля)
[avtorstudio-backup]
host=CHANGE_ME
port=5432
dbname=postgres
user=CHANGE_ME
sslmode=verify-full
sslrootcert=/etc/avtorstudio-backup/supabase-ca.crt

# rclone.conf
[supabase]
type=s3
provider=Other
env_auth=false
access_key_id=CHANGE_ME
secret_access_key=CHANGE_ME
endpoint=CHANGE_ME
region=CHANGE_ME
```

**Комплект `recovery/` обязателен**, иначе скрипт отказывается делать вид, что сервис восстановим:

- `inventory.json`: `{"project_ref":"joaxeoavjvlqmtlepkrr","reviewed":true,"source_commit":"<sha>","reviewed_at":"<date>"}`. `reviewed=true` ставит оператор только после проверки содержимого, не копировать как готовое подтверждение.
- `auth.json`: актуальные настройки Auth, SMTP, site URL, redirect allow-list, OAuth-провайдеры и необходимые секреты. Экспорт/ручная сверка через Dashboard; не считать конфигурацию из README источником истины.
- `edge.env`: все значения Edge Secrets для Telegram/VK, Робокассы, писем, cron и уведомлений; API списка секретов возвращает хэши, **они не заменяют значения**. Если исходные значения потеряны, восстановить/ротировать отдельно с владельцем до допуска к запуску.
- `operations.md`: закреплённый Git commit и способ получить код; версии PostgreSQL/Supabase; расширения, cron, nginx/DNS, сертификаты, параметры деплоя Edge и шаги пересоздания бакетов/политик. Нужные локальные конфиги и ключи положить рядом. Доступ к GitHub и DNS сохранить отдельно от VPS.

При изменении конфигурации обновлять этот комплект. Проверка наличия файлов не доказывает полноту настроек — её подтверждает восстановление. `vault.json` создаётся автоматически через `vault.decrypted_secrets`; он содержит plaintext секретов в локальном каталоге `0700`, а удалённо защищён шифрованием restic. Не открывать его в логах и не публиковать артефактом CI.

## Установка и первый запуск (после отдельного согласования VPS)

1. Проверить свободный диск, RAM, время и сетевое соединение VPS → Supabase и Yandex. Поставить Python ≥3.10, rclone с поддержкой S3, restic ≥0.16 (repo v2), PostgreSQL client **той же major-версии**, что сервер. Зафиксировать проверенные версии и источники установки в operations.md; Docker не нужен. Подключение БД и rclone проверить без публикации вывода с данными пользователей.
2. Создать системного пользователя `avtorstudio-backup` без login-shell. Установить root-owned `backup.py` в `/opt/avtorstudio-backup/`, unit-файлы — в `/etc/systemd/system/`; каталог скриптов недоступен для записи backup-пользователю. Создать state/cache каталоги с владельцем `avtorstudio-backup`, `0700`.
3. Настроить закрытые файлы. Под средой `backup.env`, от backup-пользователя выполнить `restic init --repository-version 2` **один раз**. Скрипт сам репозиторий не создаёт и не перезаписывает существующий. Выполнить `backup.py preflight`; эта проверка не подключается к БД.
4. `systemctl daemon-reload`, затем `systemctl start avtorstudio-backup.service`. Таймер пока **не включать**, `BACKUP_RETENTION_ENABLED=0`. Проверить `journalctl -u avtorstudio-backup.service`, `last-success.json`, `restic snapshots --tag avtorstudio-backup-v1`, размер в S3 и пиковое потребление VPS. Любая ошибка pg_dumpall/Vault/S3 — остановка, без молчаливого пропуска.
5. Провести восстановление ниже. Только после успешного результата поставить `BACKUP_RETENTION_ENABLED=1` и включить `systemctl enable --now avtorstudio-backup.timer`. Расписание: 03:00 МСК ±5 минут, пропущенный запуск догоняется после старта VPS. После загрузки проверка → `forget --keep-daily 14 --keep-within 14d --prune` → проверка. При нескольких запусках в сутки снимков может быть больше 14; это безопасная нижняя граница истории, не жёсткий лимит места.
6. Дождаться первого запуска по таймеру, проверить heartbeat. Отдельно отключить heartbeat-сигнал тестовой проверки и убедиться, что внешний монитор сообщает о пропуске. Без внешнего монитора падение самого VPS останется незамеченным.

## Учебное восстановление

**Никогда не восстанавливать поверх продакшена для проверки.** Создать изолированное совместимое окружение (PostgreSQL major и Supabase extensions/baseline как у источника). Его создание/стоимость согласовать отдельно. Запретить исходящие письма, Telegram-уведомления, Робокассу и cron: тест не должен списывать деньги или уведомлять пользователей.

1. С отдельного компьютера/сервера, используя сохранённый вне VPS пароль restic, выбрать конкретный snapshot ID. Выполнить `restic restore <id> --target <private-empty-directory>`. Не использовать `latest` после начала проверки. Нужны права на чтение бакета. Перед передачей архива зашифровать транспорт и ограничить доступ к каталогу.
2. `python3 backup.py verify --directory <directory>` проверяет SHA-256 **всех** файлов и читабельность TOC `pg_restore`. Это проверка артефактов, не восстановление PostgreSQL.
3. Разобрать `roles.sql` и TOC `pg_restore --list database.dump` под совместимую целевую Supabase. Управляемые роли/схемы на свежем проекте уже существуют: не запускать вслепую `--clean` или весь roles.sql. Подготовить проверенный restore-list: существующие managed-объекты не создавать повторно, пользовательские схемы/функции/политики и данные auth/storage восстановить. Сначала проба в изолированном окружении с остановкой на первой ошибке; сохранить итоговые команды/list и версии в закрытом operations.md. Это обязательная часть допуска, автоматического "restore to prod" здесь нет.
4. Восстановить значения Vault по `vault.json` через Vault API под **новым** ключом целевого окружения; старый ciphertext без исходного root key непригоден. Проверить cron и webhook-секреты, оставить задания выключенными до завершения теста. Пользовательские SQL-роли восстановить с минимальными необходимыми правами; пароли custom roles в архив не входят, задать новые при необходимости.
5. Файлы из `storage/<bucket>/<path>` загрузить через Storage API/S3 в целевые бакеты с теми же именами, настройками MIME/public/private и политиками. Согласовать метаданные `storage.objects` с реальными файлами, не считать восстановление метаданных восстановлением байтов. Если ref/домен изменились, переназначить сохранённые public URL в книгах, главах, персонажах и картах. Исходные URL в тестовой базе не должны маскировать отсутствие локальных файлов.
6. Развернуть код закреплённого commit, Auth/SMTP/OAuth/Edge Secrets из recovery-комплекта. Вход существующего **тестового** пользователя, открытие/сохранение книги, версии, иллюстрации и экспорт проверять с заблокированным доступом браузера к старому Supabase Storage. Сверить количество строк критичных таблиц, список/размеры/SHA файлов. Проверить, что цепочка восстановления работает, даже если исходный VPS недоступен.
7. Записать snapshot ID, начало/конец, версии инструментов, объёмы, команды, найденные ограничения. Если вход/файлы/версии не восстановились или вышли за рабочий день — L-3 не закрыта, таймер и автоматическую очистку не считать принятыми. Реальное переключение DNS/прода — отдельное подтверждение владельца.

## Обслуживание

- Ежедневно внешний монитор контролирует heartbeat; уведомления о расходах/размере, предупреждение при 750 МиБ и прогноз по приросту. Бэкапы не останавливать ради бесплатного лимита. Статистика `restic stats --mode raw-data` отражает данные репозитория, но не заменяет фактический billed size бакета.
- Ежемесячно `restic check --read-data` и учебное восстановление выбранного снимка; перед ним не менять источники/схему. Команды запускать тем же пользователем и с тем же flock, когда service не работает, иначе возможна конкуренция с prune. Не выполнять `restic unlock` без выяснения, что живых процессов нет.
- При ротации пароля restic сохранить новый ключ вне VPS; при изменении OAuth/платежей обновить recovery. Не удалять старые ключи до пробы восстановления.
- Отключение: `systemctl disable --now avtorstudio-backup.timer`; дождаться окончания текущего service. S3-репозиторий и ключи не удалять. Удаление копий — отдельное решение.

## Локальные проверки

```bash
python3 -m unittest discover -s deploy/backup -p 'test_*.py'
```

14 unit-тестов используют временные файлы и заглушки команд, не обращаются к Supabase/S3. Проверяют неполный источник, изменение Storage во время дампа, сбои загрузки/проверки, запрет очистки до успеха, целостность и отсутствие секретов в ошибках. При `RESTIC_TEST_BINARY=restic` дополнительный интеграционный тест создаёт настоящий локальный зашифрованный репозиторий на синтетических данных: три снимка, дедупликация, восстановление удалённого файла, очистка и повторное восстановление. CI устанавливает restic и запускает оба вида тестов. Они **не заменяют** настоящий дамп, загрузку в Yandex и восстановление Supabase.

Источники: [PostgreSQL pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html), [Supabase backup/restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore), [Storage не входит в дамп](https://supabase.com/docs/guides/platform/backups), [restic retention](https://restic.readthedocs.io/en/stable/060_forget.html).
